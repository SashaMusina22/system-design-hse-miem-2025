# Домашняя работа 2: Интеграции



## Введение
Это продолжение проектирования архитектуры системы интерактивного взаимодействия радиостанции с аудиторией, начатого в первой домашней работе. На этом этапе мы проектируем верхнеуровневую архитектуру системы, описываем интеграции между сервисами, выбираем подходящие протоколы взаимодействия и обосновываем решения.

## Цели проекта
1. Разделить функциональность на микросервисы.
2. Определить способы коммуникации между ними.
3. Обеспечить соответствие функциональным и нефункциональным требованиям (ФТ и НФТ).
4. Обеспечить масштабируемость, отказоустойчивость и безопасность.

## Архитектура системы (HLD)

### 1. Клиенты
- Веб-клиенты и мобильные устройства.
- Подключение через HTTP и WebSocket для поддержки real-time взаимодействия.

### 2. Компоненты системы

#### 2.1 API Gateway
- Точка входа для всех клиентов.
- Инкапсулирует логику маршрутизации, авторизации и балансировки нагрузки.
- Поддержка REST и WebSocket.

#### 2.2 Сервис аутентификации
- Отвечает за регистрацию, вход пользователей, управление сессиями.
- Генерация JWT токенов для авторизации.
- Хранение сессий и токенов в Redis.

#### 2.3 Сервис голосований
- Обрабатывает голосование пользователей в реальном времени.
- Работает с Redis для быстрого чтения и записи.
- Получает команды через WebSocket.

#### 2.4 Сервис заказов
- Принимает заявки на новые песни.
- Интегрируется с очередью RabbitMQ для асинхронной обработки заказов.

#### 2.5 Сервис плейлистов
- Управление текущим и будущим плейлистом диджея.
- Хранение данных в PostgreSQL.
- Позволяет диджеям видеть результаты голосования.

#### 2.6 Сервис уведомлений
- Рассылает push-уведомления и обновления в реальном времени.
- Использует WebSocket-соединения с клиентами.

### 3. Хранилища и очереди
- **PostgreSQL** — основная база данных для хранения песен, пользователей и плейлистов.
- **Redis** — хранение кэшированных данных, голосований и сессий пользователей.
- **RabbitMQ** — очередь сообщений для обработки заказов песен.

### 4. Интеграции между сервисами
| Источник → Назначение        | Протокол       | Назначение                 |
| ---------------------------- | -------------- | -------------------------- |
| Клиент → API Gateway         | HTTP/WebSocket | Входной интерфейс          |
| API Gateway → Аутентификация | REST/gRPC      | Проверка учётных данных    |
| API Gateway → Голосования    | WebSocket      | Передача голосов           |
| API Gateway → Заказы         | REST           | Передача заказов на песни  |
| API Gateway → Плейлисты      | REST           | Обновление плейлистов      |
| Заказы → RabbitMQ            | AMQP           | Постановка задач в очередь |
| Голосования → Redis          | gRPC           | Хранение голосов           |
| Аутентификация → Redis       | gRPC           | Хранение токенов и сессий  |
| Плейлисты → PostgreSQL       | SQL            | Управление песнями         |
| Уведомления → Клиенты        | WebSocket      | Отправка уведомлений       |

### 5. Дополнительные компоненты (для продакшена)
- **Load Balancer** — балансировка нагрузки (например, Nginx, HAProxy).
- **CDN** — ускорение раздачи статики.
- **Monitoring** — мониторинг состояния (Prometheus, Grafana).
- **Centralized Logging** — централизованное логирование (ELK Stack).
- **Rate Limiter** — защита от перегрузок (например, Envoy, Kong).

## Выбор технологий и протоколов
- **REST** — для взаимодействия между компонентами с CRUD-операциями.
- **WebSocket** — для real-time голосований и уведомлений.
- **gRPC** — высокопроизводительное взаимодействие внутренних сервисов.
- **RabbitMQ** — очередь задач для асинхронной обработки.
- **PostgreSQL** — реляционная БД для хранения бизнес-данных.
- **Redis** — высокоскоростной кэш и хранилище сессий.

## Соответствие требованиям (из HW_1)

### 1. Функциональные требования (ФТ)
- Голосование за песни — через WebSocket и сервис голосований.
- Заказ песен — REST API + очередь RabbitMQ.
- Просмотр результатов голосования — через сервис плейлистов.
- Уведомления пользователям — через WebSocket.

### 2. Нефункциональные требования (НФТ)
- Масштабируемость — горизонтальное масштабирование микросервисов.
- Производительность — real-time взаимодействие через WebSocket, Redis и gRPC.
- Отказоустойчивость — разнесённая архитектура, SLA 99.9%.
- Безопасность — HTTPS, JWT, соответствие ФЗ-152.
- Мониторинг и логирование — предусмотрены соответствующие системы.
