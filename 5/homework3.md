# Домашняя работа 3: Базы данных

## Введение

В данном документе подробно рассмотрен выбор баз данных и методов их использования в архитектуре интерактивной платформы для радиостанции. Основой проектирования являются функциональные и нефункциональные требования, определённые в первой домашней работе, а также разработанная архитектура из второй домашней работы.

---

## 1. Карта сервисов и используемых баз данных

- **Плейлисты:** хранение информации о песнях, исполнителях и плейлистах требует реляционной структуры с поддержкой сложных связей между сущностями. Для этого выбрана база данных PostgreSQL, которая обеспечивает высокую надёжность, поддерживает SQL-запросы, транзакционность (ACID) и хорошо подходит для аналитических задач.

- **Заказы:** система обработки заказов построена на асинхронной очереди сообщений RabbitMQ. Такой подход позволяет разделить процесс поступления и обработки заявок, обеспечивая высокую пропускную способность и отказоустойчивость.

- **Голосование:** для хранения информации о голосованиях используется in-memory база Redis. Благодаря хранению данных в оперативной памяти Redis обеспечивает минимальные задержки при обработке голосов в реальном времени.

- **Аутентификация:** данные о сессиях пользователей, их авторизации и токенах доступа также хранятся в Redis. Это позволяет быстро проверять авторизацию при каждом обращении к сервису и эффективно управлять временем жизни сессий.

- **Уведомления:** система отправки уведомлений построена на базе Redis Streams, который позволяет обрабатывать потоки сообщений и оперативно доставлять события пользователям через WebSocket.

---

## 2. Обоснование выбора баз данных

- **PostgreSQL (Плейлисты):** обеспечивает стабильное хранение данных, поддержку сложных выборок и аналитических запросов. Поддерживает индексацию, транзакционность и хорошо справляется с большими объёмами связанных данных.

- **Redis (Голосование, Аутентификация, Кэш):** обладает крайне низкими задержками чтения и записи, подходит для хранения временных данных, быстро обрабатывает большое количество запросов в реальном времени.

- **RabbitMQ (Заказы песен):** гарантирует доставку и обработку заказов, позволяет реализовать очередь с повторными попытками обработки в случае ошибок, легко масштабируется для обработки высоких нагрузок.

- **Redis Streams (Уведомления):** обеспечивает потоковую обработку и доставку уведомлений, что важно для синхронизации данных с клиентами в реальном времени.

---

## 3. Репликация

- **PostgreSQL:** используется репликация основного сервера на дополнительные копии (реплики), которые разгружают основную базу при выполнении операций чтения и служат резервными источниками данных при сбоях.

- **Redis:** применяется схема с основным сервером и резервными нодами, что позволяет обеспечить быстрый failover и минимизировать время недоступности сервиса при сбоях.

- **RabbitMQ:** настраивается кластер из нескольких серверов с зеркалированием очередей, что предотвращает потерю сообщений при сбоях отдельных нод.

---

## 4. Масштабирование

- **PostgreSQL (Плейлисты):** при росте объёма данных возможно горизонтальное разделение по пользователям или регионам. Для этого применяются расширения PostgreSQL, например, Citus.

- **Redis (Голосования, Аутентификация):** масштабируется через Redis Cluster, который автоматически распределяет данные между множеством серверов, обеспечивая равномерную загрузку.

- **RabbitMQ (Очереди заказов):** поддерживает объединение серверов в кластер, при этом очереди могут дублироваться на нескольких узлах, обеспечивая отказоустойчивость и масштабируемость.

---

## 5. Хранилище для разных действий

- Регистрация и авторизация выполняются через Redis.
- Информация о песнях, исполнителях и плейлистах хранится в PostgreSQL.
- Заказы песен поступают в очередь RabbitMQ.
- Голосование реализуется через Redis для быстрого подсчёта голосов.
- Уведомления передаются через Redis Streams с последующей доставкой через WebSocket.
